# AGENTS.md

C# **MonoGame DesktopGL** game targeting `net10.0` (see `StoreChase.csproj`). No CI, no solution file. Layout: namespace `StoreChase`, entrypoint `Program.cs` → `Game1.cs`. All gameplay files are top-level `.cs` files in the repo root. The verification harness is the one exception: it lives in `harness/StoreChase.Harness/` as its own project.

## Build / run

- Build: `dotnet build`. Run: `dotnet run`.
- Verify: `dotnet run --project harness/StoreChase.Harness` (see below).
- To edit content via the MGCB CLI: `dotnet tool restore` (pins `dotnet-mgcb` 3.8.5.1 in `dotnet-tools.json`), then use `mgcb`. Not needed for plain builds — the `MonoGame.Content.Builder.Task` package runs the content build automatically.
- To screenshot a specific camera view (the compositor blocks synthetic key input here, so U/O/V can't be driven remotely): `SC_TILT=<deg> dotnet run` overrides the opening tilt (the game opens at `Camera.DefaultTiltDegrees`, 45°), `SC_FP=1 dotnet run` starts in first person, and `SC_PLAY=1 dotnet run` skips the attract screen and starts the round immediately (read once in the `Camera` constructor / during `Initialize`; unset, nothing changes).
- **Effect compilation needs Wine on Linux/macOS.** `Content/Effects/CatNormalMap.fx` is built by MGCB, which shells out to a Windows HLSL compiler under Wine. This machine is already set up (`~/~/.winemonogame` via MonoGame's `net8_mgfxc_wine_setup.sh`), and `MGFXC_WINE_PATH` is exported from `~/.profile`/`~/.zprofile`. If a build fails with `MGFXC0001`, open a new login shell (or `export MGFXC_WINE_PATH=...`) so MGCB can find that prefix. This only bites when the `.fx` actually changes (the content task skips it otherwise) — i.e. exactly when you're least expecting it.

## Known warnings

`dotnet build` is clean (0 warnings). Keep it that way.

## Content & assets

- The MGCB content pipeline (`Content/Content.mgcb`) builds `Content/DefaultFont.spritefont` (UI text) and `Content/Effects/CatNormalMap.fx` (the cat's normal-mapped shader). `Content/Robotron.spritefont` (built from `Content/Fonts/robotron-2084.ttf`) is the attract-screen wordmark font. Everything else visual is either procedural geometry (`CubeMesh.cs`, `PersonMesh.cs`), textures generated in code (`StoreTextures.cs`), or a runtime-loaded OBJ. The player is a procedural humanoid whose arms/legs swing around joint pivots each frame (`PersonMesh` + `Game1.DrawPlayer`) — no animation assets. `Sfx.cs` synthesises every sound at startup; there are no audio files, and the whole system turns itself off if there's no audio device.
- `DefaultFont.spritefont` names the system font `DejaVu Sans`; if the content build fails with "font not found" on another machine/OS, change `<FontName>` to an installed font and rebuild (`dotnet tool restore` then `dotnet build`).
- The cat model — `Content/Models/Cat.obj`, `Cat.mtl`, `Cat_diffuse.jpg`, `Cat_bump.jpg` — is loaded **at runtime** by `ObjLoader.cs` from the relative path `Content/Models/Cat.obj`, NOT through MGCB. `StoreChase.csproj` already copies `Content\Models\**` to the output dir (`CopyToOutputDirectory`), so new model files only work if they land under `Content/Models` — do not register them in `Content.mgcb`.
- `ObjLoader` is deliberately narrow: single material, quad faces, `vt`/`vn` assumed present; uses 32-bit `int` indices (no 65,535 vertex cap). It produces `VertexPositionNormalTextureTangent` (position/normal/UV/tangent+handedness), computes tangents from UVs, and bakes the grayscale `map_Bump` height map into a tangent-space normal map. Diffuse/normal textures get a generated mip chain — every level is filled, because an incomplete chain samples black under a mipmapping sampler. If a new OBJ fails, start there.
- `ObjLoader.ParseGeometry` is the same parser with no `GraphicsDevice` and no textures (`Load` = parse + upload, sharing vertex arrays via `StaticMesh.WithTextures`). Anything that only needs geometry — the animation rig, headless tools — should use it, so that path stays testable without a display.

## Architecture

- `StoreLayout.cs` holds the floor plans: the grid, the counter span, the player start, and a generator that makes a store of any size. `StoreLayouts.All` is the list of layouts; `BigBox` (26×18) and `Standard` (18×12) are the two hand-made ones (`Standard` is the reference the alarm rates are tuned against); the campaign also generates two bigger stores (see `Campaign.cs`). The generator only ever *removes* obstacles from an aisle lattice, so connectivity is guaranteed by construction — a maze whose connectivity has to be checked is a maze that will eventually generate an unreachable shelf.
- `GridMap.cs` is pure grid logic over a `StoreLayout` and owns no graphics: walkability, BFS (`NextStepToward`, `PathTo`, `DistanceMapFrom` — the latter two memoised, since the map is immutable), `HasLineOfSight` (a Bresenham walk that shelves actually block), the counter (`IsCounter` + `CounterRow`/`CounterStart`/`CounterEnd`, which come from the layout now, not constants), and the cell enumerations (`WalkableCells`, `ShelfEdgeCells`) the spawners use. `GridPos` is defined in that same file.
- World space is X/Z with Y = up. `Game1.CellSize = 2f` world units per grid cell. `Player`/`Critter` expose `WorldPos` (X/Z, Y=0) and have **no `Draw` method** — `Game1` owns all rendering and the camera. `Player.Update(gameTime, map, moveDir, freeMove)` has two modes: grid-locked cell-to-cell (isometric; `moveDir` is a grid step) and free world-space (first-person; `moveDir` is a normalized camera-relative XZ heading, with per-axis wall sliding). Free mode keeps `Cell` synced to the nearest walkable tile so the grid-based critter AI/catch still work, and reverts to a cell center when toggled back to grid mode.
- **`Player` stops when the keys are released.** A held direction starts a new tile only while there is input; a tile already in flight is always finished. This was a bug: the old code reused the held direction to start the *next* tile too, so a player who let go of the keys walked on until it hit a shelf. There was no way to stand still in the isometric view.
- `Game1` draws the procedural meshes with a `BasicEffect` and the cat with the custom `CatNormalMap.fx` effect (normal mapping + its own key/fill/back lighting), using `DrawUserPrimitives`/`DrawUserIndexedPrimitives`. Every `CatNormalMap.fx` uniform (textures, transforms, light directions/colors, the per-species `Tint`) is pushed from C# — the effect framework does not reliably apply HLSL uniform initializers, and zeroed light colors make the shader return black (the cat renders as an invisible/black silhouette). `BasicEffect.DiffuseColor` is sticky state that multiplies the texture, so `DrawMesh` resets it to white on every draw. `BasicEffect.SpecularColor` is set to `Vector3.Zero` every frame: the three directional lights each carry a white specular term, and at 0.2 that summed to a flat ~0.36 white lift on every surface, which washed out the saturated product colours (the \"washed out\" complaint) — keep specular off for the arcade palette. Each critter owns its own parsed copy of the cat geometry (~36k vertices) because the rig rewrites vertices in place; sharing one mesh would mean every cat in frame shows whichever was drawn last, and `StartRound` must drop those meshes with the cast or every restart leaks one model per cat. The store's ambient light shifts towards red as the alarm fills (`Game1.AmbientForAlarm`), but the alarmed colour is a red *shift* (0.58, 0.33, 0.30), not a red light, so surfaces keep their identity under alarm.
- Camera logic lives in `Camera.cs` (constructed in `Game1.SetupCamera()`, driven by `Camera.Update(gameTime, input, playerWorldPos, playerFacing)`): the game opens in the angled 3/4 view at `Camera.DefaultTiltDegrees` (45°, perspective); straight-down tilt 0 is still the orthographic reference view. U/O tilt (up to `Camera.MaxTiltDegrees` = 80°), and `SC_TILT=<deg>` overrides the opening tilt. **The isometric view follows the player**: the viewport is a fixed window of `Camera.ViewCellsWide` cells across, scaled by zoom and clamped to the store's edges (`Camera.ClampToMap`), so a store bigger than the screen scrolls. The old sizing derived the view from the map's dimensions, which meant a bigger store zoomed itself out to fit and there was never anything to scroll. The camera always uses world `Up` and nudges its position slightly along +Z at tilt 0 so the look direction is never exactly vertical (no up-vector snap at the boundary). `CameraMode` also offers a `FirstPerson` mode (V / gamepad Y toggles): a 60° perspective camera at the player's head (`FirstPersonEyeHeight = 2.2`, PersonMesh's head center) with mouse-look yaw/pitch (`LookSensitivity` rad/unit, pitch clamped to ±85°). `Mode == FirstPerson` seeds yaw from `playerFacing` and pitch 0; iso pan/zoom/tilt are left intact so toggling back restores the exact view. `Game1` skips `DrawPlayer` in first-person and hides the cursor. `Camera.MapMoveToWorld` turns WASD into the camera-relative heading used by free movement (W heads where you look, S backs up, A/D strafe).
- `Camera` has a **second constructor that takes an aspect ratio instead of a `GraphicsDevice`**, so its framing maths can be tested headlessly. `Camera.FocusPoint` is the world point it is centred on.
- `EventSystem.cs` is a pub/sub singleton (`EventSystem.Instance`, namespace `StoreChase`). Game1 publishes `GameStartedEvent` (init + restart), `GameWonEvent`, `GameLostEvent`, `ItemStolenEvent`/`ItemSecuredEvent`, the power-up and hazard events (`PowerUpCollectedEvent`/`PowerUpUsedEvent`, `PlayerSlippedEvent`, `FireAlarmPulledEvent`), and `ShopPurchaseEvent`; `RunStats.cs` subscribes and logs to the console (including thefts per species, which is the cheapest read on whether one profile is too effective). Add new events as `sealed` subclasses of `BaseEvent`. `RunStats` isn't stored on `Game1` — the singleton's handler list keeps it rooted.
- `ArcadePalette.cs` is the source of truth for every colour in the game: the nine Robotron colours (`#000000` black, `#FFFFFF` white, `#FFFF00` yellow, `#FF0000` red, `#00D900` green, `#0000FF` blue, `#FF00FF` magenta, `#FF7600` orange, `#FF5100` red-orange) plus a tenth `Cyan #68FFDE` used sparingly, with role aliases (`Player`, `Cat`, `Loot`, `Wall`, `Floor`, `Accent`, `Structure`, …) and `Dim`/`Nearest`/`Entries`/`TitleLetters` helpers. `Nearest` snaps hand-mixed colours back onto the palette so nothing drifts; store textures, shelf palettes, the HUD and the attract screen all derive from it. `RainbowTitle` exposes two clocks — `Phase` (wrapped 0..1, for colour/blink) and `Time` (monotonic seconds, for motion); motion must use `Time`, not `Phase` (the latter reset caused the starfield/marquee snap).
- The attract screen (`Hud.DrawTitleScreen`) is a Robotron-style void: black background, magenta marquee band scrolling from `TitleTime`, the `STORE CHASE 3D` wordmark in `Content/Robotron.spritefont` (built from `Content/Fonts/robotron-2084.ttf`) below the bar with palette colours that march, a yellow rule, cyan subtitle, blinking prompt, bottom-anchored controls panel, and footer. Stars drift across the full viewport width from `TitleTime` with no reset snap and no centre divider rule. `SC_PLAY=1` skips it (synthetic key input is blocked in this environment).
- `StoreTextures`: the floor is dark wood planks (mean ≈ (82, 58, 38)), the walls are cool blue-grey (≈ (92, 100, 116)) so they never read as flesh, the shelf steel is mid grey, and the counter is dark with a dim yellow stripe. `ShelfMesh.AislePalette`/`ProductPalette` are `ArcadePalette.Dim` hues rather than independently mixed pastels, which is what fixed the "washed out" aisle colours.
- `Customer` walks its destination one adjacent cell at a time via `GridMap.NextStepToward` (it used to lerp the whole distance in one stride and slide through shelves). `Customer.Target` is the destination; `Customer.NextCell` is the current step's end. `CustomerBrain` is unchanged in shape.
- `Campaign.cs` is the headless run state: coin values (`CampaignState.CoinsFor`, alarm weight × 10, plus a win bonus), the shop (`ShopCatalog` in key-slot order — the catalog order **is** the display order and the key order, an invariant `Hud` and `Game1.TryBuySlot` both rely on), and the escalating round specs (`CampaignRounds.SpecFor(i)`: loot `5 + i/2` capped 8, cats `3 + i/3` capped 5, across four stores then the last repeats). `Game1` keeps one `CampaignState` for the whole run; `StartRound` reads `CurrentSpec` and rebuilds the map/items/camera/minimap when the layout changed (graphics rebuilds guarded by `_textures != null`, because the first `StartRound` runs in `Initialize` before `LoadContent`). `ItemField.ItemSecured` is the coin hook — every path to the counter (player secure, thief tackled at the till) pays exactly once. The shop buys are `Game1.TryBuySlot` (keys 1–6, `InputState.BuySlot`); consumables queue in `CampaignState` and are pocketed one per `StartRound`; the three permanents express through `SpeedFactor` (× skates), `AlarmSystem.DecayMultiplier` (decay only, `Reset` restores 1) and `SpikeFactor` (× the counter-drop spike).
- `PowerUps.cs` (one-slot `PowerUpInventory`: skates/spray/treat), `Hazards.cs` (spills + fire alarms, `HazardField`), `FxSystem.cs` (particles/texts/hit-stop, all pure state) and `Music.cs` (`MusicSynth` + a `DynamicSoundEffectInstance` fed from a background thread, mood = alarm stage only) are the newer gameplay/juice/audio systems; all four are `GraphicsDevice`-free and covered by the harness (`PowerUpChecks`, `HazardChecks`, `FxChecks`, `MusicChecks`, `CampaignChecks`).
- `RainbowTitle.cs` animates the centered "Store Chase" title. The hue phase is advanced on a **background thread**; `Hud.DrawRainbowTitle` only reads `Phase` and draws. Keep all graphics work on the game thread (SpriteBatch/GraphicsDevice aren't thread-safe) — `UnloadContent()` disposes the title's thread.
- `Hud.cs` draws the whole screen-space overlay (objective panel, alarm meter, off-screen thief marker, end banner + the between-rounds shop panel, popups) and `MessageFeed.cs` the scrolling event feed. Both are pure output: `Game1.BuildHudState` snapshots what they need each frame. `Hud.SetLayout` re-bakes the minimap when the campaign changes store.

## Input

- All device input goes through `IInputSource` (`InputState.cs` for the per-frame snapshot). `KeyboardMouseInput` and `GamePadInput` are the only files allowed to call `Keyboard`/`Mouse`/`GamePad`; `InputSystem` polls the registered sources and exposes the active device's state as `InputSystem.State` once per `Game1.Update()`. Key and button bindings live in `InputMapper` (centralized, rebindable, defaults = shipping scheme) so the sources never hardcode a key; both accept a mapper in their constructor and fall back to `InputMapper.Default`.
- `InputSystem` auto-detects the active device: it keeps the current source while it has input (`InputState.HasActivity`), otherwise hands off to the first other source with input. `ActiveDevice`/`ActiveSource` expose which is current; every source is still polled each frame so internal state (mouse wheel delta) stays current.
- First-person mouse capture is a source capability, not a gameplay concern: `IMouseLookSource` (`MouseLookEnabled`/`MouseLookCenter`) is implemented by `KeyboardMouseInput`, and `InputSystem.MouseLookEnabled`/`MouseLookCenter` are set from the camera mode in `Game1.Update` and forwarded to any source that supports it. While captured, the source reports a centered, relative look delta and re-centers the pointer (skipping the capture-start frame so entering FPS doesn't snap the view).
- `Camera.Update` takes `in InputState` (and `Player.Update` takes a resolved `moveDir` + `freeMove`, not the raw state) — do not read device APIs from gameplay code; add a source instead. `InputState` axes: `Move.Y` = +down, `Tilt` = +up, `Zoom` = wheel notches/frame, `Look` = first-person look delta (right/up positive; mouse pixels or a gamepad stick scaled to the same unit), `ToggleCamera`, `Throw` and `Use` are rising edges, and `BuySlot` is a 1-based shop slot (0 = none, so the struct default is safe; keyboard D1–D9, rising edge per key — the gamepad leaves it 0, the shop is keyboard-only); add `GamePadInput` mappings there.
- `GamePadInput` maps the Start button to a rising edge on `InputState.Start` and `InputState.Restart`, so the attract screen and the between-rounds shop can be driven from a gamepad (the shop's buy keys stay keyboard-only).

## Gameplay shape

- A run is a **campaign** of escalating stores (`Campaign.cs`): loot and cat counts grow per round (`CampaignRounds.SpecFor`), coins are banked for secured loot and wins, and a between-rounds shop (keys 1–6) sells consumable power-ups and three-tier permanents. `Game1.LootCount`/`CritterCount` remain as the *reference* workload the round simulation is tuned against; `StartRound` uses the spec's values.
- A round: items on the shelves and a cast of cats. Cats steal them; the player picks them up and secures them at the counter. The alarm fills while a cat carries something (rate scales with the *value* of what is out) or while the player carries something (much lower rate), and drains when nothing is out. `RunPhase` (`RunPhase.cs`) is Playing/Won/Lost. On a win R advances the campaign, on a loss R retries the same store.
- `ItemField` owns the items and every possession rule (steal, tackle-drop, counter-drop, pick up, secure, auto-secure when dropped on the counter). `LootItem` is a dumb data holder. The AI only *decides* to steal (`ICritterAI.WantsToSteal`); `Game1.TrySteal` performs the transfer, so possession rules stay out of the AI.
- **A thief that reaches the counter dumps the goods there and the alarm spikes** (`ItemField.AbandonAtCounter`, `Game1.CounterDropAlarmSpike`). It is the thief's escape plan and a losing one: the goods are *dropped*, not secured, so the player still has to collect them, but the alarm takes a hard hit. Without this the thief stood on the counter holding the loot forever, which made any round with a theft unwinnable. `Critter.JustArrived` is how the game knows a critter landed on a cell.
- **The goods have kinds, and the species have tastes.** `LootKind` (Canned/Boxed/Bagged) is not decorative: `LootItem.AlarmWeight` decides how much the alarm cares (a carton is worth more than a tin), and `CritterProfile.PreferredKind` + `UnpreferredThiefFactor` decide what a cat will bother with (`CritterProfile.ThiefDriveFor(kind)`). The AI needs the *item*, not just its cell, to express this — hence `CritterContext.LootTargetItem`.
- **The alarm has stages** (`AlarmStage`: Calm/Suspicious/Critical, from `AlarmSystem.SuspicionThreshold` and `CriticalThreshold`). The cats read the stage through `CritterContext.AlarmStage`: at Critical they stop caring what they want and go for the goods. The store's lighting shifts with the meter.
- **The cats tell each other** (`SharedAwareness.cs`). A cat that sees the player raises the alarm and it carries to any cat within `ShoutRadius` cells, degrading with distance. `Critter.PlayerAwareness` is a *vagueness* (zero = it can see the player itself), not a distance, so "seeing" and "hearing" can be compared directly. `SharedAwareness.Reset` is called every frame because cats are removed as they are tackled.
- `AlarmSystem` rates were tuned against a headless round simulation (see below). Re-run it after touching `StolenRate`, `PlayerCarryingRate`, `DecayRate`, `GraceSeconds` or `LootCount`. The rates are per-second and a bigger store takes longer to clear, so they are scaled by how much work the store is (`StoreLayout.AlarmScale`); without that, a bigger store is not harder but *unwinnable*. The counter-drop spike is a fixed fraction of the meter, not scaled, because it is a single event rather than a rate. `AlarmSystem.DecayMultiplier` (Calm nerves upgrade) scales decay only; `Reset()` restores it to 1 so headless tests never inherit a campaign's modifiers.
- **Power-ups** (`PowerUps.cs`): a one-slot pocket. Skates speed you up, the spray panics nearby cats for as long as you keep walking (it does not make them drop loot), the treat is dropped at your cell and lures cats within `SmartAnimalAI.TreatRadius`. Use = E / gamepad B (`InputState.Use`). A ball that lands on a cat stuns it 3s and makes it drop loot; the spray's panic does not.
- **Hazards** (`Hazards.cs`): spills (slip — grid mode you can't brake for a beat, free mode momentum lags; `Player.SlipSpeedBoost`, skates double the slip, a slipping cat drops loot) and fire alarms (Use-key priority over the power-up, one-shot, panics+startles all cats, spikes the alarm by the fixed `Game1.FireAlarmSpike`).
- **Juice** (`FxSystem.cs`): particles fade by lerping tint to black, texts rise+fade, hit-stop (`Game1.HitStopSeconds`/`HitStopScale`) crawls the sim only, and camera shake translates the frustum without moving `Camera.FocusPoint`. `Game1` owns the triggers; `Hud.DrawPopups` projects the texts.
- `Ball` is a throwable distraction, aimed along `Camera.FacingOnPlane`. It works in both camera modes, but only first person aims it meaningfully (overhead, the camera looks straight down so a throw always travels the same way). A ball that lands on a cat **stuns it for 3 seconds** and makes it drop what it was carrying; the cat stays in the game. Cats that aren't `IgnoresBall` path to a bouncing ball, but *not* a thief in the middle of an escape, which keeps a bolt for the counter honest. Its physics has two traps that both fail silently and are worth knowing before editing it: wall contact must not share a counter with floor bounces (a shared counter stopped the ball dead in mid-air once it had clipped two shelves), and rolling resistance must only apply while the ball is on the floor (applying it in mid-air gave a 0.3s time constant, so a throw died after ~4 units instead of crossing the store). A blocked step is undone by restoring the *previous* position along that axis, never by a fixed back-off distance — a cell-sized back-off puts the ball into the wall behind it.
- A collision is a tackle in **both** directions: `Critter.Update` checks whether the player is on its cell as well as whether it arrived on the player's. Checking only on arrival means a standing critter can never be caught, because the next thing it does is decide to walk away.

## Critter AI

- `ICritterAI.cs` defines `CritterContext` (a `record struct`), `DecideNextMove`, and the `WantsToSteal` / `WantsTreat` / `Pose` / `State` outputs. `State` (an `AIState`) is descriptive only — it reports what the AI decided (Patrolling/Chasing/Escaping/Fleeing/Investigating/Idle) for the HUD, debug tools and harness; nothing in gameplay branches on it, and `Critter.State` overrides it to `Stunned` while a stun runs. `CritterLocus` (in `Critter.cs`) is the per-frame bundle of world facts the game hands the critters — map, player cell, ball cell, loot target, alarm stage, and two delegates for loot. Rebuild it each frame; it's a struct of two delegates, and it keeps the per-critter sight state out of the shared context.
- `SmartAnimalAI` is profile-driven: every species difference lives in `CritterProfile` (a sealed record with `For(kind)` and `Random(rng)`), so a new species is a new record rather than a new class. The decision priority order is documented at the top of the file and mirrored in the README — keep the two in sync.
- `CanSeePlayer` (LOS + `VisionRadius`) and `BeingWatched` (`Camera.IsInViewCone`) are deliberately separate: the first is what the AI reacts to, the second is what a Nervous cat freezes on. Both are set by `Game1.UpdateAwareness`. In first person `IsInViewCone` is a real cone; overhead the camera looks straight down, so a cone would cover the whole store and mean nothing, and the test is instead "is it on screen" (`Camera.IsOnScreen`, a view-projection test). That only became meaningful once the store grew past the viewport.
- `CatAnimator.cs` procedurally poses the cat — legs, knees, spine, head, tail — deriving every pivot and weight from the mesh's own geometry as fractions of its bounding box, and rewriting vertices in place each frame. Poses come from `CatPose` and are eased toward, so state changes blend rather than snap. **The amplitude caps are load-bearing**: a rigid mesh shears wherever a blend rotates some vertices by a fraction of the angle. The head band is gated by *height* and the tail band by *width* on top of their Y bands, because the front paws share the head's Y range and the haunches share the tail's. Don't raise these numbers without re-measuring (below).

## Verifying changes

`dotnet build` alone will not catch a broken rig, an unbalanced alarm, or a lost item. The harness already exists — run it:

```
dotnet run --project harness/StoreChase.Harness
```

It exits non-zero on failure, so it works as a smoke test. It has three parts, plus the modes `--geometry`, `--rig`, `--rounds`, `--trace` (one round, frame by frame) and `--sweep` (play many rounds at a range of alarm settings):

- **simulate full rounds** with a scripted player at the real `Player` grid speed, asserting the heist rules: no duplicate or vanishing items, nothing in two hands, both outcomes reachable, a passive player never wins, no deadlock. This found three real bugs — an item orphaned in the `Held` state when a thief was tackled at the counter (`Secured` was clearing `Held` unconditionally), a `NearestLoose` sort key that made a chasing player oscillate between two items forever, and a thief that reached the counter and stood there holding the loot forever.
- **measure the rig** for edge stretch per body region (head/tail/legs/torso) against the rest pose. Treat >2.5× on a visible edge (rest length > 0.5 units) as tearing. `dotnet build` cannot catch a rig that reads fine in source and is a shapeless blob on screen — that's how the first pass of the pose table got caught. **Measure each pose against a freshly parsed mesh**: the rig rewrites the vertices in place, so sharing one mesh between poses measures every pose against the previous pose's deformed geometry.
- **smoke-test the pure geometry builders** (`CubeMesh`, `PersonMesh`) and the graphics-free subsystems with plain assertions. These are the pieces the round simulation never touches, and they changed vertex type during the texture work, so a bad UV or a bad normal would be fatal at startup and invisible to every other check. Assert on the *invariants* (UVs reach the repeat counts, normals are unit length, the cube still sits on the floor, line of sight is blocked by a shelf) rather than on golden values. The ball's travel distance came out of this one. The suite now also covers the grid (pathfinding, distance maps, bounds), the input layer (device hand-off, InputMapper defaults) and the camera's mode toggle.

It also checks the camera's framing (the viewport is smaller than the store, the view follows the player, the view never leaves the floor plan, the far side is off screen), the loot kinds (each species takes what it wants and leaves what it does not), the shared awareness (a cat that cannot see the player still hears about them if it is close enough), the power-up pocket, the hazards, the juice layer's state maths, the music synth, and the campaign (coin math, shop buy/afford/max/queue rules, upgrade factors, round escalation, every store on the path being playable). That's ~250 checks.

Keep new gameplay systems free of `GraphicsDevice` dependencies so this stays possible. If a class needs a `GraphicsDevice` only for its geometry, give it a device-free constructor like `Camera` has.

## Repo gotchas

- `.gitignore` ignores `bin/`, `obj/`, `Content/bin`, `Content/obj`, `.vs/`, `.vscode/`. Don't re-add build artifacts. `artifacts/` holds the original cat model upload (`.zip` + extracted files) and is intentional to keep.
- `StoreChase.csproj` excludes `harness/**/*.cs` from its own compile. The root project globs `**/*.cs`, so without that exclusion the harness's `Program.cs` is compiled into the game as well and collides with the game's top-level statements (CS7022).
- README.md is the detailed design/decision log (camera math, OBJ orientation analysis, rig rationale, alarm balance). Trust it for intent, but verify code-level claims against the source — some have gone stale, and the harness is how to check.

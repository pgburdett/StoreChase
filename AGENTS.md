# AGENTS.md

Single-project C# **MonoGame DesktopGL** game targeting `net10.0` (see `StoreChase.csproj`). No tests, no CI, no solution file. Layout: namespace `StoreChase`, entrypoint `Program.cs` → `Game1.cs`. All gameplay files are top-level `.cs` files in the repo root.

## Build / run

- Build: `dotnet build`. Run: `dotnet run`.
- To edit content via the MGCB CLI: `dotnet tool restore` (pins `dotnet-mgcb` 3.8.5.1 in `dotnet-tools.json`), then use `mgcb`. Not needed for plain builds — the `MonoGame.Content.Builder.Task` package runs the content build automatically.
- **Effect compilation needs Wine on Linux/macOS.** `Content/Effects/CatNormalMap.fx` is built by MGCB, which shells out to a Windows HLSL compiler under Wine. This machine is already set up (`~/~/.winemonogame` via MonoGame's `net8_mgfxc_wine_setup.sh`), and `MGFXC_WINE_PATH` is exported from `~/.profile`/`~/.zprofile`. If a build fails with `MGFXC0001`, open a new login shell (or `export MGFXC_WINE_PATH=...`) so MGCB can find that prefix. This only bites when the `.fx` actually changes (the content task skips it otherwise) — i.e. exactly when you're least expecting it.

## Known warnings

`dotnet build` is clean (0 warnings). Keep it that way.

## Content & assets

- The MGCB content pipeline (`Content/Content.mgcb`) builds `Content/DefaultFont.spritefont` (UI text) and `Content/Effects/CatNormalMap.fx` (the cat's normal-mapped shader). Everything else visual is either procedural geometry (`CubeMesh.cs`, `PersonMesh.cs`), textures generated in code (`StoreTextures.cs`), or a runtime-loaded OBJ. The player is a procedural humanoid whose arms/legs swing around joint pivots each frame (`PersonMesh` + `Game1.DrawPlayer`) — no animation assets. `Sfx.cs` synthesises every sound at startup; there are no audio files, and the whole system turns itself off if there's no audio device.
- `DefaultFont.spritefont` names the system font `DejaVu Sans`; if the content build fails with "font not found" on another machine/OS, change `<FontName>` to an installed font and rebuild (`dotnet tool restore` then `dotnet build`).
- The cat model — `Content/Models/Cat.obj`, `Cat.mtl`, `Cat_diffuse.jpg`, `Cat_bump.jpg` — is loaded **at runtime** by `ObjLoader.cs` from the relative path `Content/Models/Cat.obj`, NOT through MGCB. `StoreChase.csproj` already copies `Content\Models\**` to the output dir (`CopyToOutputDirectory`), so new model files only work if they land under `Content/Models` — do not register them in `Content.mgcb`.
- `ObjLoader` is deliberately narrow: single material, quad faces, `vt`/`vn` assumed present; uses 32-bit `int` indices (no 65,535 vertex cap). It produces `VertexPositionNormalTextureTangent` (position/normal/UV/tangent+handedness), computes tangents from UVs, and bakes the grayscale `map_Bump` height map into a tangent-space normal map. Diffuse/normal textures get a generated mip chain — every level is filled, because an incomplete chain samples black under a mipmapping sampler. If a new OBJ fails, start there.
- `ObjLoader.ParseGeometry` is the same parser with no `GraphicsDevice` and no textures (`Load` = parse + upload, sharing vertex arrays via `StaticMesh.WithTextures`). Anything that only needs geometry — the animation rig, headless tools — should use it, so that path stays testable without a display.

## Architecture

- `GridMap.cs` is pure grid logic and owns no graphics: walkability, BFS (`NextStepToward`, `DistanceMapFrom`), `HasLineOfSight` (a Bresenham walk that shelves actually block), the counter row (`IsCounter` + `CounterRow/CounterStart/CounterEnd`), and the cell enumerations (`WalkableCells`, `ShelfEdgeCells`) the spawners use. `GridPos` is defined in that same file. Map layout is a hardcoded string array, 18×12.
- World space is X/Z with Y = up. `Game1.CellSize = 2f` world units per grid cell. `Player`/`Critter` expose `WorldPos` (X/Z, Y=0) and have **no `Draw` method** — `Game1` owns all rendering and the camera. `Player.Update(gameTime, map, moveDir, freeMove)` has two modes: grid-locked cell-to-cell (isometric; `moveDir` is a grid step) and free world-space (first-person; `moveDir` is a normalized camera-relative XZ heading, with per-axis wall sliding). Free mode keeps `Cell` synced to the nearest walkable tile so the grid-based critter AI/catch still work, and reverts to a cell center when toggled back to grid mode.
- `Game1` draws the procedural meshes with a `BasicEffect` and the cat with the custom `CatNormalMap.fx` effect (normal mapping + its own key/fill/back lighting), using `DrawUserPrimitives`/`DrawUserIndexedPrimitives`. Every `CatNormalMap.fx` uniform (textures, transforms, light directions/colors, the per-species `Tint`) is pushed from C# — the effect framework does not reliably apply HLSL uniform initializers, and zeroed light colors make the shader return black (the cat renders as an invisible/black silhouette). `BasicEffect.DiffuseColor` is sticky state that multiplies the texture, so `DrawMesh` resets it to white on every draw. Each critter owns its own parsed copy of the cat geometry (~36k vertices) because the rig rewrites vertices in place; sharing one mesh would mean every cat in frame shows whichever was drawn last, and `StartRound` must drop those meshes with the cast or every restart leaks one model per cat. Camera logic lives in `Camera.cs` (constructed in `Game1.SetupCamera()`, driven by `Camera.Update(gameTime, input, playerWorldPos, playerFacing)`): isometric is the default — orthographic top-down at tilt 0, perspective FOV once tilted (U/O, up to 80°). The camera always uses world `Up` and nudges its position slightly along +Z at tilt 0 so the look direction is never exactly vertical (no up-vector snap at the boundary). `CameraViewMode` also offers a `FirstPerson` mode (V / gamepad Y toggles): a 60° perspective camera at the player's head (`FirstPersonEyeHeight = 2.2`, PersonMesh's head center) with mouse-look yaw/pitch (`LookSensitivity` rad/unit, pitch clamped to ±85°). `Mode == FirstPerson` seeds yaw from `playerFacing` and pitch 0; iso pan/zoom/tilt are left intact so toggling back restores the exact view. `Game1` skips `DrawPlayer` in first-person and hides the cursor. `Camera.MapMoveToWorld` turns WASD into the camera-relative heading used by free movement (W heads where you look, S backs up, A/D strafe).
- `EventSystem.cs` is a pub/sub singleton (`EventSystem.Instance`, namespace `StoreChase`). Game1 publishes `GameStartedEvent` (init + restart), `GameWonEvent`, `GameLostEvent`, and `ItemStolenEvent`/`ItemSecuredEvent`; `RunStats.cs` subscribes and logs to the console (including thefts per species, which is the cheapest read on whether one profile is too effective). Add new events as `sealed` subclasses of `BaseEvent`. `RunStats` isn't stored on `Game1` — the singleton's handler list keeps it rooted.
- `RainbowTitle.cs` animates the centered "Store Chase" title. The hue phase is advanced on a **background thread**; `Game1.DrawRainbowTitle` only reads `Phase` and draws. Keep all graphics work on the game thread (SpriteBatch/GraphicsDevice aren't thread-safe) — `UnloadContent()` disposes the title's thread.

## Input

- All device input goes through `IInputSource` (`InputState.cs` for the per-frame snapshot). `KeyboardMouseInput` and `GamePadInput` are the only files allowed to call `Keyboard`/`Mouse`/`GamePad`; `InputSystem` polls the registered sources and exposes the active device's state as `InputSystem.State` once per `Game1.Update()`.
- `InputSystem` auto-detects the active device: it keeps the current source while it has input (`InputState.HasActivity`), otherwise hands off to the first other source with input. `ActiveDevice`/`ActiveSource` expose which is current; every source is still polled each frame so internal state (mouse wheel delta) stays current.
- First-person mouse capture is a source capability, not a gameplay concern: `IMouseLookSource` (`MouseLookEnabled`/`MouseLookCenter`) is implemented by `KeyboardMouseInput`, and `InputSystem.MouseLookEnabled`/`MouseLookCenter` are set from the camera mode in `Game1.Update` and forwarded to any source that supports it. While captured, the source reports a centered, relative look delta and re-centers the pointer (skipping the capture-start frame so entering FPS doesn't snap the view).
- `Camera.Update` takes `in InputState` (and `Player.Update` takes a resolved `moveDir` + `freeMove`, not the raw state) — do not read device APIs from gameplay code; add a source instead. `InputState` axes: `Move.Y` = +down, `Tilt` = +up, `Zoom` = wheel notches/frame, `Look` = first-person look delta (right/up positive; mouse pixels or a gamepad stick scaled to the same unit), `ToggleCamera` and `Throw` are rising edges; add `GamePadInput` mappings there.

## Gameplay shape

- A round: 5 items on the shelves (`Game1.LootCount`), 3 cats (`Game1.CritterCount`). Cats steal them; the player picks them up and secures them at the counter. The alarm fills while a cat carries something (rate scales with how many are in flight) or while the player carries something (much lower rate), and drains when nothing is out. `RunPhase` (`RunPhase.cs`) is Playing/Won/Lost.
- `ItemField` owns the items and every possession rule (steal, tackle-drop, pick up, secure, auto-secure when dropped on the counter). `LootItem` is a dumb data holder. The AI only *decides* to steal (`ICritterAI.WantsToSteal`); `Game1.TrySteal` performs the transfer, so possession rules stay out of the AI.
- `AlarmSystem` rates were tuned against a headless round simulation (see below). Re-run it after touching `StolenRate`, `PlayerCarryingRate`, `DecayRate`, `GraceSeconds` or `LootCount`.
- `Ball` is a throwable distraction, first-person only, aimed along `Camera.FacingOnPlane`. Cats that aren't `IgnoresBall` path to it, including thieves mid-escape — which is how you pull one off a good hiding place. Its physics has two traps that both fail silently and are worth knowing before editing it: wall contact must not share a counter with floor bounces (a shared counter stopped the ball dead in mid-air once it had clipped two shelves), and rolling resistance must only apply while the ball is on the floor (applying it in mid-air gave a 0.3s time constant, so a throw died after ~4 units instead of crossing the store). A blocked step is undone by restoring the *previous* position along that axis, never by a fixed back-off distance — a cell-sized back-off puts the ball into the wall behind it.
- A collision is a tackle in **both** directions: `Critter.Update` checks whether the player is on its cell as well as whether it arrived on the player's. Checking only on arrival means a standing critter can never be caught, because the next thing it does is decide to walk away.

## Critter AI

- `ICritterAI.cs` defines `CritterContext` (a `record struct`), `DecideNextMove`, and the `WantsToSteal` / `Pose` outputs. `CritterLocus` (in `Critter.cs`) is the per-frame bundle of world facts the game hands the critters — map, player cell, ball cell, loot target, and two delegates for loot. Rebuild it each frame; it's a struct of two delegates, and it keeps the per-critter sight state out of the shared context.
- `SmartAnimalAI` is profile-driven: every species difference lives in `CritterProfile` (a sealed record with `For(kind)` and `Random(rng)`), so a new species is a new record rather than a new class. The decision priority order is documented at the top of the file and mirrored in the README — keep the two in sync.
- `CanSeePlayer` (LOS + `VisionRadius`) and `BeingWatched` (`Camera.IsInViewCone`) are deliberately separate: the first is what the AI reacts to, the second is what a Nervous cat freezes on. Both are set by `Game1.UpdateAwareness`. This is why the overhead camera is a real cost rather than a neutral view — from up there the cone is ~180°, so nothing is ever pinned.
- `CatAnimator.cs` procedurally poses the cat — legs, knees, spine, head, tail — deriving every pivot and weight from the mesh's own geometry as fractions of its bounding box, and rewriting vertices in place each frame. Poses come from `CatPose` and are eased toward, so state changes blend rather than snap. **The amplitude caps are load-bearing**: a rigid mesh shears wherever a blend rotates some vertices by a fraction of the angle. The head band is gated by *height* and the tail band by *width* on top of their Y bands, because the front paws share the head's Y range and the haunches share the tail's. Don't raise these numbers without re-measuring (below).

## Verifying changes

`dotnet build` alone will not catch a broken rig, an unbalanced alarm, or a lost item. All of `GridMap`, `Critter`, `SmartAnimalAI`, `ItemField`, `AlarmSystem` and `Ball` are graphics-free by design, and `ObjLoader.ParseGeometry` needs no `GraphicsDevice`, so a console project referencing `StoreChase.csproj` can:

- **simulate full rounds** with a scripted player at the real `Player` grid speed, asserting the heist rules: no duplicate or vanishing items, nothing in two hands, both outcomes reachable, no deadlock. This found two real bugs — an item orphaned in the `Held` state when a thief was tackled at the counter (`Secured` was clearing `Held` unconditionally), and a `NearestLoose` sort key that made a chasing player oscillate between two items forever.
- **render and measure the rig** with a small software rasterizer, reporting edge stretch per body region (head/tail/legs/torso) against the rest pose. Treat >2.5× on a visible edge (rest length > 0.5 units) as tearing. `dotnet build` cannot catch a rig that reads fine in source and is a shapeless blob on screen — that's how the first pass of the pose table got caught.
- **smoke-test the pure geometry builders** (`CubeMesh`, `PersonMesh`) and the graphics-free subsystems with plain assertions. These are the pieces the round simulation never touches, and they changed vertex type during the texture work, so a bad UV or a bad normal would be fatal at startup and invisible to every other check. Assert on the *invariants* (UVs reach the repeat counts, normals are unit length, the cube still sits on the floor, line of sight is blocked by a shelf) rather than on golden values. The ball's travel distance came out of this one.

Keep new gameplay systems free of `GraphicsDevice` dependencies so this stays possible.
